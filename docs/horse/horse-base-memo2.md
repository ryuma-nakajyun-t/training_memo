# スケジュール制御 とは
スケジュール制御とは、

「処理を決められた日時や順番で実行する仕組み」

です。

例えば、

毎日0時にバッチ処理を実行する
1時間ごとにCSVを取り込む
A処理が終わったらB処理を実行する
特定の日時にデータを配信する

といった実行タイミングを管理することを指します。

IT業界では次のような意味で使われます。

分野	スケジュール制御の例シ
ステム運用	夜間バッチ実行
Spring Boot	@Scheduled による定期実行
Linux	cron による定期起動
メディアサーバ	指定時刻に動画配信
ジョブ管理	前処理→本処理→後処理の順序制御

今回開いている「メディアスケジューラシステム」であれば、

「動画・コンテンツを指定した日時に配信し、終了したら別のコンテンツへ切り替える制御」

を指す可能性が高いです。


# リアルタイム更新処理　とは​‌
リアルタイム更新処理とは、

「データの変更をすぐに画面やシステムへ反映する処理」

です。

例えば、

株価が秒単位で更新される
チャットの新着メッセージが自動表示される
在庫数が購入直後に変わる
動画配信の番組情報が即座に切り替わる

といった処理です。

スケジュール制御との違い
用語	意味スケジュール制御	決められた日時に実行する
リアルタイム更新処理	変更が発生したら即座に反映する

例：

12:00になったら動画を切り替える → スケジュール制御
管理画面で番組を変更したら即反映 → リアルタイム更新処理
職務経歴書向けに短く書くなら

リアルタイム更新処理：データ変更を即時にシステムへ反映する機能

さらに短くするなら、

リアルタイム更新：最新データを即時反映する処理

です。メディアサーバ案件なら、

番組編成・配信情報のリアルタイム更新処理

という記載が実務的な表現になります。

# 番組プレイリスト制御システム開発　
「番組プレイリスト制御システム開発」とは、
放送・配信・デジタルサイネージなどで、
「いつ・どこで・何を流すか」を制御するシステムの開発
を指します。現在見ている求人では、競馬場や場外馬券売場のディスプレイへ映像やオッズ情報を配信するためのスケジューラ開発が該当しています。

具体的には次のような処理です。

プレイリスト（番組表）の作成
指定時刻でのコンテンツ切替
緊急テロップや速報へのリアルタイム切替
配信先ごとの出し分け
配信機器への制御命令送信
スケジュールデータ（CSV、JSON、XMLなど）の生成・管理

ITエンジニア視点で言うと、
``text
コンテンツ管理
      ↓
プレイリスト生成
      ↓
スケジューラ
      ↓
配信サーバ
      ↓
ディスプレイ・放送設備
```
という流れの中で、特にスケジューラ部分を開発する仕事です。

あなたのこれまでの経験で例えると、
```text
CSV読込
ファイル管理
バッチ処理
スケジュール制御
Java開発
Linux運用
```
あたりはかなり親和性があります。

逆に放送業界特有なのは、
- SCTE-35
- ストリーミング配信
- エンコーダ制御
- デジタルサイネージ
- メディアサーバ
などの知識です。

要するに一言でいうと、
```text
「放送・配信分野のジョブスケジューラ開発」
```
に近い仕事です。  
SQL中心の業務システムよりも、時間制御・配信制御・リアルタイム処理の要素が強い案件ですね。

# これ何が難しいの？
率直に言うと、  
「画面を作ること」自体はそれほど難しくないです。  

難しいのは画面の裏側です。  
例えばオッズ一覧画面なら、  
```text
馬番
馬名
単勝オッズ
人気順位
```
を表示するだけなら、
```sql
SELECT * FROM odds
```
してThymeleafで表示するだけです。  
これは一般的な業務システムと同じです。

この案件で難しくなりそうなのは、  

### ① リアルタイム更新
普通の業務システム
```text
検索
↓
結果表示
↓
終わり
```

オッズ画面
```text
表示中
↓
5秒後更新
↓
10秒後更新
↓
15秒後更新
```
発走直前は数秒ごとに変化します。  
つまり  
- WebSocket
- ポーリング
- 非同期通信
が関係します。

### ② 時間による自動切替
例えば
```text
09:00 ニュース
09:30 CM
09:35 オッズ
09:40 レース映像
```

なら
利用者がボタンを押さなくても
```text
時刻到達
↓
自動切替
```
しなければなりません。
ここは業務システムより制御システム寄りです。

### ③ 障害時の復旧
例えば
```text
オッズ配信停止
```
したら、
```text
再接続
再取得
復旧
```
が必要です。
顧客管理システムなら多少遅れてもよいですが、
競馬場の大型モニタは止まると困ります。

### ④ 状態管理
これが意外と難しい。
例えば
```text
発売前
↓
発売中
↓
締切
↓
確定
```
状態によって画面表示が変わります。

プログラムでは
```java
enum RaceStatus {
    BEFORE,
    OPEN,
    CLOSED,
    FIXED
}
```
みたいな設計になります。
業務システム経験者でも苦戦しやすい部分です。

### ⑤ 監視画面
案件説明に  
- 運用監視
- メディアサーバ
がある場合、  
画面は作れるが  
- どのサーバが落ちたか
- どのコンテンツを再生中か
- どの配信先が異常か  
を管理するロジックが難しいです。

逆にあなたの場合、  
最近学習している  
- Spring Boot
- MVC
- PostgreSQL
- SQL
- CSV取込
- ファイル移動
- Linux
はかなり近いです。

足りない可能性が高いのは  
- WebSocket
- Scheduler
- 非同期処理
- 状態遷移設計
です。

なので、  
「画面項目が難しい案件」ではなく、「リアルタイム性と状態管理が難しい案件」  
だと思った方が実態に近いですね。

むしろ画面そのものは、  
```text
検索
一覧
登録
編集
削除
監視
```
という業務システムでよく見る構成になる可能性が高いです。
